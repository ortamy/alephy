# Смотритель архитектуры — инструкция

> **Что это:** агент, который сверяет документацию проекта с тем, что реально лежит на диске, и сообщает о расхождениях.
>
> **Файл:** `docs/03-AI/ARCH-KEEPER.md`
> **Статус:** активный
> **Когда понадобится:** после крупной правки кода, перед рефакторингом, при сомнении «а правильно ли описан проект?».

---

## Зачем он нужен

Документация расходится с кодом тихо. Замена числа в описании не вызывает
ни ошибок, ни тестов: паспорт продолжает выглядеть гладко, но врёт. Так в
`ARCHITECTURE.md` годами значилось «127 корней» при 329 на диске, а раздел
про `tools/` описывал восемь подкаталогов, которых не было никогда.

Смотритель закрывает именно эту дыру. Он **не решает**, правильна ли
архитектура, — он показывает, где описание разошлось с реальностью.

## Как запустить

### В лаборатории

1. Откройте **Конвейеры** (`#pipelines`) или **Мастерскую** (`#workbench`).
2. Выберите карточку **«Смотритель архитектуры»**.
3. Нажмите запуск. Запрос по умолчанию: `проверь архитектуру`.

### В командной строке

```bash
cd products/agents
python main.py "проверь архитектуру"
```

### Через API

```bash
curl -X POST http://127.0.0.1:5000/api/pipelines/arch_keeper/run \
  -H "Content-Type: application/json" \
  -d '{"query": "проверь архитектуру"}'
```

Сервер должен быть запущен: `python server.py` в каталоге `products/agents`.

## Что он проверяет

| Что | Как именно |
| --- | --- |
| Паспорт архитектуры | Числа вида «N корней», «N CSS-файлов» и пути внутри репозитория |
| Схема связей `GRAPH.md` | Узлы схемы (файлы) и маршруты хабов против реестра лаборатории |
| Документ об агентах | Число агентов и существование каждого упомянутого `.py` |
| Генерируемые блоки паспорта | Три таблицы между маркерами `<!-- alephy:auto:* -->` |
| Реестры агентной системы | Карточки лаборатории, пайплайны, эндпоинты и движки |

## Как читать результат

Находки попадают в три корзины — они означают разное и требуют разного:

| Корзина | Что значит | Что делать |
| --- | --- | --- |
| `auto` | Правда однозначна: неверное число или путь | Исправить по факту |
| `adr` | Расхождение затрагивает решение: слой исчез, хаб переехал | Решить и записать в `docs/decisions.md` |
| `manual` | Оценочная формулировка: автоматика подменила бы мысль | Переформулировать вручную |

Корзина `adr` — самая ценная: именно она означает, что слоя больше нет, а
описание об этом ещё не знает.

## Почему он ничего не меняет

**По умолчанию Смотритель только смотрит.** Это осознанное ограничение: агент,
который сам пишет нормативный документ, не может проверить свою же работу.
Фактическую часть паспорта он перерисовывает, ручную — никогда.

Разрешить запись:

```bash
curl -X POST http://127.0.0.1:5000/api/pipelines/arch_keeper/run \
  -H "Content-Type: application/json" \
  -d '{"query": "проверь архитектуру", "writeEnabled": true}'
```

Даже с флагом запись безопасна: пересобираются только индексы навигации,
затем запускается гейт `tools/check-docs.py`, и при красном результате
изменения **откатываются**.

## Если ничего не находится

Ноль находок может означать две разные вещи: документ правда совпадает с
диском — либо проверка молчит. Второе уже случалось дважды (неверный путь к
документу и опечатка в ключе). Поэтому у проверки есть канарейки — тесты,
которые намеренно ломают копии документов и требуют, чтобы агент это заметил
(`ArchCanaryTest`). Если вы сомневаетесь в результате, посмотрите на них: они
показывают, что система действительно ищет.

## Известные ограничения

- Проверяются только числа и пути. Смысловой дрейф ручного текста («около 50
  модулей», когда их 67) не ловится: для этого нужен разбор смысла, а он
  пока не подключён — решение и его цена описаны в ADR-010.
- Узлы схемы, не называющие конкретного файла, не проверяются.
- Раздел `docs/03-AI/` целиком не проверяется: в промптах и примерах числа
  цитируются как образец, и сверка дала бы шум (ADR-013).
