1. ОБЩАЯ АРХИТЕКТУРА

Система построена по принципу «Оркестратор + Пайплайны». Запрос проходит через три слоя.

-------------------------------------------------------------
|  СЛОЙ 1: ВЕБ-ИНТЕРФЕЙС (Research Lab)                     |
|  Пользователь нажимает кнопку «Запустить агентов»         |
|  ↓                                                         |
|  СЛОЙ 2: API-СЕРВЕР (server.py / Flask)                   |
|  Принимает запрос, возвращает результат в JSON            |
|  ↓                                                         |
|  СЛОЙ 3: МУЛЬТИ-АГЕНТНАЯ СИСТЕМА (Python)                |
|  Оркестратор → Пайплайн → Агенты → Данные                |
-------------------------------------------------------------

2. СТРУКТУРА ПАПОК И ФАЙЛОВ

Все файлы находятся в папке products/agents/.

-- products/agents/main.py -- Точка входа для командной строки (CLI).
-- products/agents/server.py -- Точка входа для веб-API (Flask).
-- products/agents/orchestrator.py -- Маршрутизатор, который решает, какой пайплайн запустить.
-- products/agents/pipelines/ -- Пайплайны (цепочки вызовов агентов).
-- products/agents/agents/ -- Модули агентов, по одному в файле. Состав и число не приводятся здесь намеренно: список живёт в автоблоке «Агентный слой» паспорта архитектуры и генерируется с диска, поэтому вручную перечисленный счёт всегда отстаёт от кода.
-- products/agents/utils/context.py -- Доступ к данным (загрузка JSON, поиск).
-- products/agents/.env -- Переменные окружения (API-ключи).
-- products/agents/requirements.txt -- Зависимости Python.
-- products/agents/ARCHITECTURE.md -- Данный документ.

3. ОРКЕСТРАТОР (orchestrator.py)

Оркестратор принимает запрос и определяет, какой пайплайн запустить. Он работает по логике ключевых слов: первое слово или устойчивая фраза запроса выбирает пайплайн.

Известные команды (полный список в `orchestrator.py`, `ROUTES`):

- «разбери слово …» → `word_analyzer`
- «сравни стих …» → `verse_comparator`
- «собери исследование …» → `research_builder`
- «обратный перевод …» / «переведи обратно …» → `paleo_translation`
- «проверь отчёт …» / «аудит исследования …» → `research_audit`
- «сканер подмен …» → `mechanism_scanner`
- «реконструируй стих …» → `verse_reconstruction`
- «самокритика …» → `critique_loop` (цикл)
- «карантин пропусков …» → `gap_cycle` (цикл)
- «хук свива …» / «спираль …» → `spiral_swiva` (спираль)
- «диалектика …» → `dialectic_loop` (цикл)
- «мидраш …» → `midrash_recursion` (цикл)
- «шмита …» → `shmita_loop` (цикл)
- «проверь архитектуру …» / «следи за архитектурой …» → `arch_keeper` (цикл)

Если запрос не совпадает ни с одной командой, возвращается ошибка «Неизвестный тип запроса» — молчаливого дефолта больше нет: система не подменяет запрос исследователя.

4. ПАЙПЛАЙНЫ (pipelines/)

Каждый пайплайн — строго определённая цепочка вызовов агентов. Движок находится в `pipelines/core.py`.

**Тип `linear` (по умолчанию).** Агенты вызываются по очереди. Если агент вернул пустой результат (`None` или `{}`), пайплайн останавливается.

**Тип `loop` и `spiral`.** Циклы с обратной связью. Выполняется виток `cycle_steps`, затем агент сходимости (`agents/convergence.py`) снимает «подпись» витка и решает: поток сошёлся (эмет — «Шаббат», остановка), принёс новые улики (поток) или повторяется без валидности (Мавет — нужен ручной разбор). Защита от вечного круга: `max_iterations`; после исчерпания витков цикл помечается как `stalled`. Опция `shmita_every` каждые N витков прощает накопленный «шум» (сброс полей), сохраняя ключевые (`query`, `trace`, `result`) — циклы освобождения вместо вечного повторения.

Линейные пайплайны:

- `word_analyzer.py` — исследователь → семитолог → разоблачитель → редактор → сборщик.
- `verse_comparator.py` — компаратор → критик → редактор → сборщик.
- `research_builder.py` — архитектор потока → связной → технический писатель → сборщик.
- `paleo_translation.py` — исследователь → переводчик палео → семитолог → проверяющий → редактор → сборщик. Обратный перевод: термины → палео-образ → параллели → сверка.
- `research_audit.py` — ревьюер → критик → проверяющий → редактор → сборщик. Карта «эмет / шекер» для готового исследования.
- `mechanism_scanner.py` — исследователь → разоблачитель → критик → сборщик. Диагностика типа искажения и механизма подмены.
- `verse_reconstruction.py` — компаратор → переводчик палео → разоблачитель → проверяющий → сборщик. Восстановление палео-смысла стиха независимо от переводов.

Циклические пайплайны:

- `critique_loop.py` — цикл «редактор → критик → проверяющий» до валидного витка без новых замечаний.
- `gap_cycle.py` — карантин пропусков: разоблачитель копит пропуски корпуса в честную карту до сатурации.
- `spiral_swiva.py` — спираль Хук Свива: связной на каждом витке расширяет горизонт; остановка — сатурация.
- `dialectic_loop.py` — компаратор (тезис) против критика (антитезис); сходимость либо эмет, либо задокументированный Шеол.
- `midrash_recursion.py` — переводчик палео входит в собственный вывод и перечитывает образ как термин до стабилизации.
- `shmita_loop.py` — «самокритика» с шмита-сбросом шума каждые 2 витка; в результате фиксируются `shmita_resets`.
- `arch_keeper.py` — Смотритель архитектуры: сканер снимает факты с диска, критик сверяет ручной текст паспорта с этими фактами, планировщик раскладывает находки в корзины `auto` / `adr` / `manual`, писатель считает дрейф автоблоков и (по явному разрешению) их перерисовывает; сходимость — по паре «снимок + целевой текст».

Кастомные пайплайны из UI без Python-раннера исполняются через карту русских имён агентов (`server.AGENT_FUNCTIONS`): линейная цепочка собирается динамически, поэтому карточки, созданные в Research Lab, больше не «фантомы» — они запускаются локально.

5. АГЕНТЫ (agents/)

Ключевые агенты:

- `researcher.py` — находит корни и стихи в roots.json через `utils/context.py`.
- `paleo_translator.py` — собирает буквы в палео-образ; в режиме `recursive` перечитывает собственный вывод как термин (мидраш-рекурсия).
- `semitologist.py` — фиксирует семитские параллели (аккадский, арамейский, угаритский).
- `exposer.py` — отмечает сдвиги между образом и переводом и копит `gaps` — карту пропусков корпуса.
- `comparator.py` — сравнивает свидетелей: LXX, ТМ, Кумран.
- `critic.py` — проверяет ход работы по критериям эмет / шекер; возвращает `critique_notes`.
- `verifier.py` — валидирует обязательные поля (`verify_targets` или `query`/`trace` по умолчанию).
- `editor.py` — приводит материал к стилю проекта и учитывает замечания критика.
- `convergence.py` — агент сходимости циклов: снимает подпись витка, считает `delta`, ставит статус «эмет» / «поток» / «Мавет» / «Тоху».
- `collector.py` — собирает единый отчёт; для циклов добавляет `iterations`, `converged`, `stalled`, `gaps`, `shmita_resets`.
- `code_reviewer.py`, `flow_architect.py`, `liaison.py`, `writer.py`, `ai_engineer.py`, `frontend.py` — служебные роли (порядок потока, связь, оформление, заглушки разработки).

Смотритель архитектуры (`arch_keeper`):

- `arch_scanner.py` — снимок фактов без интерпретаций: слои репозитория и счётчики, точки входа с проверкой существования, реестры агентов/пайплайнов/карточек лаборатории, метрики корпуса лаборатории, недавняя активность git. LLM не вызывается. Полный снимок кэшируется в пределах процесса и не попадает в пакет (иначе ответ раздувался до мегабайтов); в пакет уходит сводка.
- `arch_critic.py` — сверяет **ручной** текст паспорта с фактами: числа вида «N корней / N CSS-файлов» и внутрирепозиторные пути. Содержимое автоблоков из проверки исключено — там числа истинны по построению. Числа, совпадающие с диском, находкой не считаются; оценочные формулировки уходят не в «исправить», а в ручную корзину. Отдельно проверяются соседние документы: `GRAPH.md` (узлы схемы и маршруты против диска и реестра лаборатории) и **этот самый `AGENT-ARCHITECTURE.md`** — числа вида «N агентами» и существование каждого упомянутого `.py`. Последнее нужно системе, чтобы она проверяла документацию о себе самой.
- `arch_planner.py` — раскладывает находки в три корзины: `auto` (правда однозначна), `adr` (узел схемы исчез или хаб переехал — нужно решение человека), `manual` (оценка, автоматика подменила бы мысль). Предложения не применяются — только формулируются.
- `arch_writer.py` — перерисовывает только содержимое маркеров `<!-- alephy:auto:* -->` в `docs/01-ARCHITECTURE/ARCHITECTURE.md`. Ручной текст не трогает: критик может найти в нём дрейф, но исправляет его человек. По умолчанию работает как dry-run; запись разрешается флагом `write_enabled` и только после `generate-docs-index.py` (STATS.md считает строки паспорта, поэтому индексы пересобираются до гейта) и зелёного `check-docs.py`; при красном гейте запись откатывается.
- `arch_convergence.py` — сходимость по подписи «снимок + целевой текст + список дрейфующих блоков». Если репозиторий не меняется, а блоки расходятся, виток получает статус «Мавет» и передаётся человеку.
- Право записи в проект есть только у `arch_keeper`, и только по явному флагу: с белого списка `server.WRITABLE_PIPELINES`. Любой другой пайплайн игнорирует `writeEnabled` — список проверяется на сервере, а не на стороне интерфейса, поэтому подделать его из браузера нельзя.

Граница ответственности: агент фиксирует расхождение описания с диском, но не решает, что архитектура неверна. Решения остаются за человеком и фиксируются в `docs/decisions.md`.

Проверка самой проверки: `ArchCanaryTest` подставляет заведомо дрейфующие копии документов во временную папку и требует, чтобы агент их нашёл. Тест «сейчас ноль находок» ловит регрессию, канарейки — саму способность находить; ни один из них не заменяет другой (ADR-014).

Каждый агент экспортирует функцию `(data) -> data`: принимает пакет от предыдущего агента и возвращает обновлённый пакет. След каждого вызова пишется в `trace` и `agentTrace` (с номером `iteration`), чтобы цикл был виден, а не скрыт.

6. ДАННЫЕ (utils/context.py)

Файл context.py отвечает за загрузку и поиск данных. Он определяет все пути к корневым папкам проекта и работает с файловой системой.

-- load_roots() -- Загружает roots.json из папки researchlab/data/roots/.
-- find_root(query) -- Ищет корень по запросу в roots.json.
-- find_term_files(query) -- Ищет .md-файлы в content/terminology/ по имени или содержимому.
-- find_tanakh_verse_context(ref) -- Ищет упоминания ссылки на стих (например, «Берешит 1:1») в content/tanakh/.
-- load_instruction(rel_path) -- Загружает шаблоны инструкций из папки instructions/.
-- slugify(text) -- Преобразует текст в URL-дружественный формат.

7. API-СЕРВЕР (server.py)

Сервер написан на Flask. Он принимает POST-запросы на эндпоинт /run и раздаёт интерфейс ResearchLab.

**Запуск (одна команда):**
cd products/agents
python server.py                # http://127.0.0.1:5000 — откроет Лабораторию в браузере
python server.py --port 9000    # другой порт
python server.py --no-cors      # без CORS-заголовков
python server.py --no-browser   # без автооткрытия браузера

**Запуск из интерфейса:** раздел «AI → Запуск сервера» в Лаборатории — статус сервера
(поллинг /api/health + /api/info), кнопки «Остановить» / «Перезапустить» (POST /api/lab/shutdown,
POST /api/lab/restart), «Открыть лабораторию» и генерация start-server.bat / stop-server.bat
для первого запуска. Также в products/agents лежат готовые start-server.bat и stop-server.bat.

**Эндпоинты управления процессом:**
GET  /api/health             — статус;
GET  /api/info               — pid, python, cwd, uptime;
POST /api/lab/shutdown       — остановка сервера;
POST /api/lab/restart        — перезапуск в новом окне (Windows).
GET  /apps/researchlab/      — интерфейс Лаборатории.

Запрос на /run содержит JSON-тело с полем query. Например: {"query": "разбери слово Берешит"}.

Сервер передаёт строку запроса в orchestrator.dispatch(), получает результат и возвращает его в формате JSON.

8. ИНТЕГРАЦИЯ С RESEARCH LAB (ВЕБ-ИНТЕРФЕЙС)

Чтобы сайт мог вызывать агентов, в Research Lab нужно добавить JavaScript-код, который отправляет POST-запрос на локальный сервер.

Пример кода для сайта:
fetch('http://localhost:5000/run', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ query: "разбери слово Берешит" })
})
.then(res => res.json())
.then(data => console.log(data));

Этот код можно поместить в карточку «AI-Агенты» или в любую другую точку интерфейса, откуда пользователь может отправлять запросы.

10. РАСШИРЕНИЕ СИСТЕМЫ

Чтобы добавить нового агента:
1. Создать файл agents/new_agent.py.
2. Определить в нём функцию run(data), которая принимает данные и возвращает результат.
3. Импортировать этого агента в нужный пайплайн.
4. Вставить вызов этого агента в цепочку внутри пайплайна.

Чтобы добавить новый пайплайн:

**Линейный:** создать `pipelines/new_pipeline.py`, импортировать шаги из `agents/` и использовать `run_steps` из `pipelines/core.py`. Зарегистрировать в `orchestrator.ROUTES` и `orchestrator.PIPELINES`, добавить карточку в `pipelines.json` (поля `runner`, `type`, `name`, `agents`).

**Циклический:** в `run(query)` использовать `run_loop` и передать `converge_step=converge` из `agents/convergence.py`. В реестр карточек добавить `"type": "loop"` (или `"spiral"`) и `maxIterations`.

Правила циклов:

- Каждый виток инкрементирует `data["iteration"]`; агенты обязаны писать в пакет, а не в глобальное состояние.
- Виток обязан заканчиваться агентом, который кладёт `data["converged"]` — иначе движок «кружит» до `max_iterations` и помечает результат как `stalled` (Мавет).
- Пустой результат любого шага останавливает и линейный, и циклический пайплайн.
