# Архитектурные решения (ADR)

### ADR-021: Три карточки на существующих агентах вместо пяти декоративных
- Дата: 2026-10-06
- Статус: accepted
- Контекст: аудит конвейеров нашёл два изъяна реестра. Первый: часть агентов (`frontend.py`, `ai_engineer.py`) не вызывалась ни одним пайплайном — модули есть, пути исполнения нет. Второй: `docs/03-AI/AGENT-PIPELINES.md` обещал пайплайны и агентов, которых в коде нет (`cleaner`, `docs_manager`, `tester`, `designer`, `validator`, `connector`, `idea_generator`). Соблазн закрыть разрыв — добавить карточку под каждый обещанный сценарий.
- Решение: добавлены три карточки, и каждая закрывает изъян работающим кодом. `witness_council` — новый тип композиции (веер, ADR-019). `ui_canon` вызывает `frontend.prepare`, который действительно читает CSS лаборатории и считает расхождения канона §4.1a; итог аудита становится заголовком результата через явное поле `data["summary"]` в сборщике. `registry_audit` вызывает `arch_scanner.scan` и показывает, где карточка осталась без раннера, раннер без карточки, а модуль пайплайна без карточки; он ничего не пишет — документ архитектуры правит только `arch_keeper` по явному разрешению. Отвергнуты `code_canon`, `experiment_ai`, `claim_ledger`, `docs_sync`, `slop_gate`: первые три были бы перестановкой существующих цепочек (`research_audit` уже ведёт ревьюера через критика и проверяющего), а `docs_sync` и `slop_gate` требуют агентов, которых нет, — карточка с заглушкой обещала бы работу, которой не делает.
- Альтернативы: (1) добавить все пять карточек и ждать агентов — отвергнуто: реестр из карточек-обещаний и есть та болезнь, которую нашёл аудит; (2) те же цепочки под новыми именами — отвергнуто: восемь почти одинаковых циклов уже показали цену такого «разнообразия»; (3) сначала написать недостающих агентов — отложено: это отдельные решения (что делает `cleaner`, кто даёт ему право удалять файлы) и отдельные ADR.
- Последствия: реестр карточек — 17 записей, и каждая исполняется. `ui_canon` считает по диску (тест требует `frontend.titles > 0`), `registry_audit` ничего не пишет (тест сравнивает байты документа архитектуры до и после). `docs/03-AI/AGENT-PIPELINES.md` переписан под фактический реестр и больше не обещает выдуманных агентов; числа в него не возвращены — иначе решение ADR-016 («документ без таблицы чисел не берём под надзор») пришлось бы пересматривать.

### ADR-020: Тип карточки из UI исполняется движком (`loop` / `spiral`), а не только показывается
- Дата: 2026-10-06
- Статус: accepted
- Контекст: карточка, созданная в Research Lab, может объявить `type: loop` и `maxIterations`, и интерфейс честно печатает «Витков максимум». Но сервер собирал для такой карточки линейную цепочку (`run_steps`) и шёл по ней ровно один раз: `maxIterations` не значил ничего, а `collector` не получал `iterations` и `converged`. Пользователь видел тип «Цикл» и линейный по сути прогон, а результат не содержал ни истории витков, ни вердикта сходимости.
- Решение: `server.run_card_pipeline()` выбирает движок по данным карточки: `loop`/`spiral` → `run_loop` с `converge_step=agents.convergence.converge` и `maxIterations` из карточки (иначе 5), линейный тип → `run_steps`. Карточка, не завершившая работу Сборщиком, получает собранный результат: без него запуску нечего показать. `spiral` исполняется тем же `run_loop`, потому что спираль задаётся агентами витка (`liaison` расширяет горизонт), а не отдельным механизмом. Заодно в паспорте пайплайна появилась строка «Итог цикла» (эмет / Мавет и число витков) — вердикт приезжал в результате, но интерфейс его не показывал.
- Альтернативы: (1) убрать тип и `maxIterations` из формы создания — отвергнуто: данные карточки описывают не только интерфейс, и удаление поля не сделало бы цикл возможным; (2) считать `spiral` линейной цепочкой — отвергнуто как подмена смысла; (3) завести отдельный движок спирали — отвергнуто: `run_loop` плюс `liaison` уже дают спираль (`spiral_swiva`), отдельный механизм был бы дублем.
- Последствия: `test_custom_loop_card_runs_engine_loop` держит сходимость и историю витков для карточки без раннера, `test_custom_linear_card_has_no_cycle_fields` — то, что линейная карточка полей цикла не получает. Теперь тип в карточке — обязательство движка: если он заявлен, витки будут, а `maxIterations` ограничит их честно, вплоть до статуса «Мавет».

### ADR-019: Веер как первоклассный примитив движка (`run_fanout`)
- Дата: 2026-10-06
- Статус: accepted
- Контекст: движок знал ровно два вида композиции — линейную цепочку (`run_steps`) и цикл (`run_loop`). Всё разнообразие реестра достигалось перестановкой одних и тех же агентов, а «несколько независимых проходов по одному вопросу» выразить было нечем: попытка свести две линии требовала либо приватного кода в пайплайне, либо выдачи линейной цепочки за веер. Что схема исчерпана, видно по самим данным: в реестре восемь почти одинаковых циклов (`critique_loop`, `shmita_loop`, `gap_cycle`, `midrash_recursion`, `spiral_swiva` и др.), отличающихся только набором шагов и параметрами.
- Решение: в `pipelines/core.py` добавлен `run_fanout(data, branches=..., join=...)`. Каждая ветка получает `deepcopy` входного пакета с полем `branch_id`, поэтому улики ветки не видны соседним — иначе «независимость» была бы только словом. Пустой результат ветки не останавливает веер: ветка помечается пустой в `data["branches"]`, а решение о сведении принимает `join` — обычные шаги над общим пакетом, куда поля веток слились по порядку (порядок веток = приоритет при совпадении имён). Первый потребитель — пайплайн `witness_council`: три независимых прохода (текстовые свидетели, палео-образ, карта подмен) и общее сведение проверяющим, критиком и сборщиком.
- Альтернативы: (1) `run_quorum` (голосующие плюс судья, вердикт эмет / шекер) — отложено: независимых голосующих среди детерминированных агентов нет, три одинаковых голоса «согласны» всегда, то есть кворум был бы театром, а не проверкой; примитив вернётся вместе с LLM-шагом, у которого есть провайдер; (2) `run_dag` с `depends_on` — отложено как преждевременное обобщение: веер покрывает известные сценарии, а граф без второго потребителя — архитектура ради архитектуры; (3) параллельные ветки через `ThreadPoolExecutor` — отвергнуто: шаги синхронные и детерминированные, ввод-вывода нет, выигрыша нет, а след становится нечитаемым; (4) приватный веер внутри одного пайплайна — отвергнуто: композиция тогда не проверяется тестами движка и каждый новый пайплайн повторял бы её по-своему.
- Последствия: композиция стала проверяемым контрактом движка (`FanoutEngineTest`: изоляция копий, пустая ветка, сводка «кто что принёс», слияние следов). В карточке `witness_council` «Исследователь» повторён трижды — это честное отражение трёх начал веток, а не дубль: порядок шагов совпадает с порядком `trace`, иначе срез этапа приписал бы шагу чужие данные. Кворум и граф остаются в бэклоге с явной причиной отказа, а не «на будущее».

### ADR-018: Паспорт Оркестратора — control-plane в общем реестре паспортов
- Дата: 2026-10-06
- Статус: accepted
- Контекст: `#ai-agents/<id>` рисует общий шаблон (ЗАПУСК / СВЯЗИ / РЕЗУЛЬТАТ), а секцию «ПАСПОРТ АГЕНТА» (§5.2q) и тулбар (§4.7) получают только агенты с флагом `passport` в `getAgentMapData()`. Оркестратор был единственным исключением (`passport: false`), потому что это не исполняемый агент-процессор с контрактом `(data) -> data`, а control-plane: генератор `tools/generate-agent-passports.py` строил паспорта из импортируемых модулей `agents/*.py`, а `orchestrator.py` лежит уровнем выше. Страница Оркестратора честно отражала его особый статус, но выпадала из канона остальных двадцати агентов. Побочно аудит нашёл дефект реестра: генератор уже вставлял Оркестратора в `agent-passport-manifest.js`, а `getAgentMapData()` добавлял его же вторым `unshift` — в списке было 22 записи, «Оркестратор» дублировался, а detail открывался без паспорта, потому что `.filter(id)[0]` брал первую (хардкодную) запись с `passport: false`.
- Решение: Оркестратор получает собственный статический паспорт `data/agents/orchestrator.json`, собранный из `products/agents/orchestrator.py` только через AST (без импорта — иначе генератор тянул бы все пайплайны). Контракт описывает `dispatch()`/`run_pipeline()`, задачи строятся из `ROUTES` («Подставить» кладёт фразу в поле ЗАПУСК), capabilities — control-plane (`execution`/`readRepository`/`writesFiles` = false, `streaming` = true). Хардкод Оркестратора из `render_manifest` убран: запись берётся из того же payload-а, что и все остальные. В `getAgentMapData()` второй `unshift` заменён дополнением записи на месте (иконка `ui/arrows`, `featured` для статуса «Активен») с fallback, если манифест не загружен. Флага `passport: false` в реестре больше нет.
- Альтернативы: (1) оставить Оркестратора без паспорта как control-plane — отвергнуто прямым требованием: страница должна читаться как страницы остальных агентов; (2) дать паспорт без кодовой части — отвергнуто: `orchestrator.py` — реальный модуль с точками входа, а паспорт без фактов о диске повторял бы ошибку выдуманных значений (§6); (3) импортировать `orchestrator` в генераторе наравне с `agents/*` — отвергнуто: это тянет 14 пайплайнов и их зависимости в сборку статики, где нужен только AST-разбор; (4) оставить дубль и скрыть вторую запись фильтром — отвергнуто: лечило бы симптом, а источник (два владельца одной записи) остался бы.
- Последствия: список агентов возвращается к 21 записи без дубля; `test_passports_cover_registered_executable_agents`, `test_generated_passport_is_fresh` и новый `test_orchestrator_passport_is_control_plane` держат паспорт свежим; `data/agents/orchestrator.json` теперь в том же контракте, что остальные, и собирается тем же генератором. Побочно исправлена иконка шапки detail: записи реестра не несут поля `icon`, и `agent.icon + '.png'` давал `undefined.png`, затирая базовую иконку модуля; теперь override иконки ставится только когда она объявлена, а базовый `crafts/hammer-and-chisel.png` не затирается.

### ADR-017: Кнопка записи в интерфейсе — отдельное действие с подтверждением, а не флаг запуска
- Дата: 2026-10-02
- Статус: accepted
- Контекст: пайплайн `arch_keeper` умел перерисовывать фактические блоки (ADR-009), и право записи было на сервере (белый список `WRITABLE_PIPELINES` плюс флаг `writeEnabled` в теле запроса). Но в интерфейсе кнопки не было: агент умел менять файлы проекта, а человек мог получить этот результат только через `curl`. Развилка была продуктовой: оставить запись только через API (безопасно, но функция спрятана) или дать кнопку в карточке пайплайна.
- Решение: в карточке пайплайна с признаком `writable: true` в `data/pipelines.json` появляется кнопка «Применить изменения». Она вызывает отдельную функцию `applyPipeline`, а не `runPipeline` с дополнительным аргументом: у обычного «Запустить» физически нет пути передать `writeEnabled`. Перед запросом — `window.confirm`, текст которого перечисляет, что именно изменится (блоки между маркерами `alephy:auto` и отчёт дрейфа) и что ручной текст не трогается. Признак `writable` в данных — подсказка интерфейса, а не право: сервер по-прежнему сверяется со своим белым списком и игнорирует флаг у любого другого пайплайна.
- Альтернативы: (1) флаг в теле обычного запуска — отвергнуто: у «Запустить» и «Применить изменения» разные последствия, а одна кнопка с двумя режимами означала бы, что случайный клик правит репозиторий; (2) кнопка без подтверждения — отвергнуто: запись меняет отслеживаемые файлы, а откат без git возможен только вручную; (3) вынести запись в отдельный маршрут `#pipelines/<id>/apply` — отложено: пока единственный писатель это `arch_keeper`, отдельный маршрут ради одной кнопки даст лишнюю поверхность; если писателей станет двое, маршрут станет оправдан; (4) показывать кнопку всем карточкам и полагаться на отказ сервера — отвергнуто: интерфейс не должен предлагать действие, которое заведомо будет отклонено.
- Последствия: в интерфейсе появился единственный путь, который правит файлы проекта из браузера, и он защищён тремя независимыми барьерами: признаком в данных, подтверждением пользователя и белым списком на сервере. Кнопка гасится вместе с остальными серверными контролами, когда агентный сервер недоступен (общий `updatePipelineServerStatus`), потому что запись без сервера невозможна. Статус чипа после применения различает «Записано» и «Без правок» — оба состояния означают успех, но пользователю важно видеть, менялось ли что-то на диске.

### ADR-016: `AGENT-PIPELINES.md` и `AGENT-STATUS.md` проверены отдельно и в надзор не введены
- Дата: 2026-10-02
- Статус: accepted
- Контекст: ADR-013 отложил разбор этих двух документов «отдельной задачей — уместно для них, неуместно для промптов». Разведка выполнена: по каждому файлу прогнаны `check_claims`, `check_paths` и проверка существования упомянутых модулей агента. Результат: `AGENT-PIPELINES.md` — ноль находок по всем трём проверкам; `AGENT-STATUS.md` — ноль находок по числам и модулям, одна по путям.
- Решение: ни один из двух документов не добавляется в автоматический надзор. Граница проверки остаётся на трёх документах из ADR-011 и ADR-012. Единственная находка разведки устранена вручную: в шапке `AGENT-STATUS.md` был указан несуществующий путь `docs/03-AI/AGENT-STATUS.MD.md` — опечатка с двойным расширением, исправлена на фактическое имя файла.
- Альтернативы: (1) добавить оба документа в `check_agent_doc` — отвергнуто по данным разведки: проверка даёт на них ноль, то есть надзор без единого срабатывания за всё время существования; нулевой мониторинг хуже его отсутствия, потому что читатель начинает считать файл проверенным; (2) добавить в надзор только `AGENT-PIPELINES.md` как реестр пайплайнов — отвергнуто: документ не содержит ни одного числового утверждения о количестве пайплайнов, поэтому сверять нечего, а сверка имён пайплайнов потребовала бы новой проверки с собственным форматом разбора и своим шумом на строках-примерах; (3) считать `AGENT-STATUS.md` источником правды о состоянии и проверять против него репозиторий — отложено: это обратная задача (не надзор документа, а надзор кода по документу), и она противоречит ADR-009, где источником правды объявлен диск, а не проза.
- Последствия: разведка закрыта, гипотеза ADR-013 не будет проверяться заново. Правило, которое из неё следует и которое стоит помнить: добавление документа в надзор — не безответственное «на всякий случай», а утверждение, что проверка на нём что-то поймает; если прогон молчит, документ не добавляется. Если `AGENT-PIPELINES.md` однажды обзаведётся таблицей пайплайнов с числами, решение пересматривается.

### ADR-015: Дрейф архитектуры проверяется в CI, но не блокирует merge
- Дата: 2026-10-02
- Статус: accepted
- Контекст: ADR-009…ADR-014 закрыли вопрос «умеет ли агент находить дрейф», но проверка жила только в пайплайне и в тестах: её запускал человек через интерфейс или вручную через unittest. Репозиторий при этом меняется каждый день, а паспорт переписывается вручную — дрейф накапливался незамеченным между прогонами. Нужен был автоматический аудит, но поднимать `server.py` во всех CI-задачах нельзя: это Flask-зависимость ради проверки, которая по сути не HTTP.
- Решение: добавлен `tools/check-architecture-drift.py` — read-only вход в ту же систему. Скрипт импортирует агентов напрямую (`agents.arch_scanner`, `agents.arch_critic`, `agents.arch_planner`), прогоняет сканер → критик → планировщик и печатает находки; шаги с правом записи (`arch_writer`, `arch_convergence`) не вызываются вообще, поэтому инструмент физически не может изменить файл. Режим по умолчанию возвращает код 1 при находках, `--warn` всегда возвращает 0, `--markdown` даёт таблицу для `$GITHUB_STEP_SUMMARY`. CI-workflow `.github/workflows/architecture-audit.yml` запускает его в режиме `--warn` и публикует отчёт артефактом.
- Альтернативы: (1) блокирующий режим (код 1 в CI) — отвергнуто: дрейф паспорта почти всегда возникает как побочный эффект обычной правки кода, и блокировка merge превратит агента в обязательный ритуал каждого PR; кроме того, до первого прогона с правом записи это гарантированно красная сборка, то есть CI перестают читать; (2) гонять пайплайн через `server.py` в CI — отвергнуто: аудит не нуждается в HTTP, а зависимость от работающего сервера в задаче без сервисов делает её хрупкой; (3) переиспользовать шаги пайплайна напрямую вместо дублирования вызовов — частично принято: вызываются те же функции критика и планировщика, но список источников перечислен в скрипте явно, без `record()` и пакета; дублирование списка — осознанная цена за отсутствие зависимости от сервера, оно ловится тестом-канарейкой; (4) отдельный триггер только на `docs/**` — отвергнуто: дрейф появляется и от правки исходников (новый пайплайн, новый агент), так что триггер на документах пропускал бы ровно те изменения, ради которых проверка существует.
- Последствия: аудит виден в каждом PR, затрагивающем `docs/`, агентный слой или исходники лаборатории, и ничего не меняет на диске — по умолчанию он безопасен. Отчёт об дрейфе остаётся дедупликацией: то, что workflow только показывает, пользователь применяет кнопкой «Применить изменения» или вручную. Список документов под надзором не расширялся (ADR-016), и потому workflow даёт одинаковый результат независимо от состояния раздела `docs/03-AI/`. Побочный эффект: `--warn` в CI означает, что красный статус job невозможен — сигнал живёт в step summary и артефакте, и это сделано намеренно.

### ADR-014: Проверку проверяет канарейка, а не тест «сейчас чисто»
- Дата: 2026-10-02
- Статус: accepted
- Контекст: система сверки архитектуры дважды вела себя как исправная, будучи сломанной. Один раз `check_agent_doc` молчал, потому что путь к документу считался от пути паспорта и уводил в корень репозитория; второй раз `render_report` падал на `KeyError`, но это выглядело как проблема инструментов, а не кода. Оба раза тесты проходили, потому что проверяли одно и то же утверждение: «на текущем документе ноль находок». Такое утверждение истинно и для проверки, которая ничего не проверяет.
- Решение: добавлен `ArchCanaryTest` — дрейф создаётся намеренно во временных копиях документов (константы `ARCHITECTURE_DOC`, `GRAPH_DOC`, `AGENT_DOC` подменяются), после чего агент обязан найти его. Канарейки шесть: неверное число, несуществующий путь, мёртвый узел схемы, маршрут-призрак в реестре, несуществующий модуль в документе об агентах и прохождение находки до планировщика. Тест «сейчас чисто» сохранён — он ловит регрессию на текущем состоянии, но канарейки ловят саму способность находить.
- Альтернативы: (1) полагаться на ручной прогон пайплайна — отвергнуто: именно ручной прогон и показывал «ноль» у нерабочей проверки; (2) сломать настоящий документ в рабочем дереве на время прогона — отвергнуто: тест обязан быть безопасным при параллельном запуске и не оставлять мусор при падении; (3) только счётчик находок в тестах — отвергнуто: счётчик ноль одинаков для исправной и сломанной проверки, это ровно та ловушка, которую пришлось закрыть; (4) внешний скрипт-верификатор вместо теста — отложено: пока развёртывание только локальное, unittest даёт то же самое бесплатно и участвует в обычном прогоне.
- Последствия: подмена документов делается временными файлами, реальные `docs/` тесты не трогают, но требуют аккуратного восстановления констант — за это отвечает `addCleanup`. Канарейки поймали ошибку в самих себе: первые версии использовали кириллические имена (`#выдуманный-хаб`, `выдуманный_агент.py`), которые не совпадают с латинскими шаблонами реестра, и проходили вхолостую — то есть канарейка способна притворяться зелёной так же, как и проверка, поэтому её данные должны быть реалистичными, а не удобными. Правило для будущих проверок: тест на «сейчас ноль» полезен, но недостаточен — рядом с ним обязателен хотя бы один кейс с заведомо плохими данными.

### ADR-013: Проверку паспорта не распространяем на весь раздел `docs/03-AI/`
- Дата: 2026-10-02
- Статус: accepted
- Контекст: после ADR-012 логично было расширить те же проверки на остальные 14 документов `docs/03-AI/` — там почти наверняка есть числа и списки пайплайнов, которые уже разошлись. Разведка (одноразовый прогон `check_claims` и `check_paths` по каждому файлу раздела) дала 25 находок, и подавляющее большинство — ложные: `AI-MODELS.md` содержит «Создай 100 корней для roots.json», где 100 — часть примера промпта, а не утверждение о состоянии репозитория; `NEW-CHAT-PROMPT.md` и `CHAT-PROMPT.md` цитируют служебные и исторические пути (`tools/cache/…`, `products/website/server.js`) как иллюстрации. Настоящая находка была одна, и она уже закрыта в ADR-012.
- Решение: границу проверки оставить на трёх документах — паспорт, схема связей, документ об агентной системе. Остальные документы раздела не проверяются числами: в них числа и пути цитируются как примеры, в промптах и исторических заметках, и автоматическая сверка даст шум, который научит читателя игнорировать находки. Вывод разведки фиксируется здесь, чтобы гипотезу не проверяли заново.
- Альтернативы: (1) распространить проверку чисел на весь раздел — отвергнуто по данным разведки: минимум 24 находки из 25 ложные, а ложные срабатывания в отчёте об архитектуре опаснее пропусков, потому что подрывают доверие ко всей проверке; (2) добавить фильтр «пропускать строки со словом “пример”» — отвергнуто как принципиально ненадёжно: пример может не содержать этого слова, а утверждение может содержать («создай 15 паков» — задание, «15 паков» — факт), поэтому фильтр ловил бы не то и не всё; (3) проверять только пути во всём разделе — отвергнуто: те же цитаты исторических путей дают тот же шум, а польза ограничена документами архитектуры, которые уже проверяются; (4) разбирать каждый документ раздела отдельно и решать по нему — отложено как отдельная задача: уместно для `AGENT-PIPELINES.md` и `AGENT-STATUS.md`, где числа описывают текущее состояние, и неуместно для промптов.
- Последствия: раздел `docs/03-AI/` остаётся зоной без автоматического надзора, и это осознанный размен: полнота уступлена в пользу отсутствия шума. Если появится документ, который целиком описывает текущее состояние агентной системы, его нужно добавить в проверку явно — вместе с тестом на ноль находок, иначе проверка за один файл перестанет быть проверкой. Настоящая находка разведки (`AGENT-ARCHITECTURE.md` с неверным числом агентов и несуществующим модулем) уже исправлена в ADR-012 — разведка оказалась не бесполезной, она показала, где смотреть, и закрыла там одну настоящую ошибку.

### ADR-012: Агент проверяет документацию о собственной агентной системе
- Дата: 2026-10-02
- Статус: accepted
- Контекст: после ADR-011 оставалась очевидная дыра: `docs/03-AI/AGENT-ARCHITECTURE.md` — документ, который читают, когда разбираются в агентах, — не проверялся ничем. В нём стояло «папка с 16 агентами», хотя на диске их 22, и упоминался модуль `frontend_developer.py`, которого не существует (файл называется `frontend.py`). Обе ошибки пережили несколько рефакторингов, потому что любая ручная цифра в документации стареет молча: её не проверяет ни гейт, ни человек, читающий документ по нужде, а не ради инвентаризации.
- Решение: `arch_critic` получил проверку `check_agent_doc` — числа вида «N агентами» / «N пайплайнов» и существование каждого упомянутого `.py` сверяются с агентным слоем (корень `products/agents` и подпапки `agents/`, `pipelines/`, `utils/`). Метрики `agents` и `agent_pipelines` добавлены в `arch_scanner.scan_lab_metrics`, чтобы числа проверялись из того же снимка фактов, а не из отдельного обхода. Отдельно: путь к документу теперь берётся из общей константы `DOCS_DIR`, а не вычисляется от пути паспорта — неверный расчёт давал тихий ноль находок вместо проверки.
- Альтернативы: (1) просто исправить две цифры и не проверять — отвергнуто: это ровно то состояние, из которого выросли обе ошибки; число «16» отстало от кода молча, и через месяц отстанет снова; (2) проверять только числа — отвергнуто: несуществующий `frontend_developer.py` важнее неверного счётчика, потому что читатель ищет по нему файл; (3) генерировать весь `AGENT-ARCHITECTURE.md` — отвергнуто: документ объясняет, почему пайплайн устроен так, а не только перечисляет, что есть; (4) проверять все документы `docs/03-AI/` — отложено: критерии факта определены для паспорта, схемы и агентного документа; для остальных потребуется разбор, иначе получится источник шума; (5) заменить число в тексте ссылкой на автоблок — отвергнуто как единственная мера, но применено в строке о составе папки: число там больше не приводится, потому что пересчитывается агентом.
- Последствия: первая же проверка дала две настоящие находки, обе исправлены, и обе были старше текущей работы над агентами. Тест `test_current_agent_doc_has_no_drift` требует нуля находок на текущем документе, поэтому следующий забытый модуль уронит тесты, а не тихо разойдётся с кодом. Проверка молчала бы при двух условиях, и оба закрыты тестами: неверный путь к документу (`test_agent_doc_is_found`) и расхождение метрик с диском (`test_counts_come_from_disk`).

### ADR-011: Схема связей `GRAPH.md` проверяется наравне с паспортом
- Дата: 2026-10-02
- Статус: accepted
- Контекст: ADR-009 и ADR-010 научили систему сверять паспорт с диском, но `docs/01-ARCHITECTURE/GRAPH.md` остался вне проверки — при том что это второй документ, который читают, чтобы понять границы проекта. Схема в mermaid перечисляет узлы с путями (`Router[LabRouter<br/>js/router.js]`) и ключевые маршруты хабов, и ничто не следило, что эти пути и хабы ещё существуют. Тот же класс ошибок, что ADR-009 закрыл для паспорта: переехал файл, а схема продолжает на него ссылаться. При этом в самой `GRAPH.md` уже было записано предостережение «не восстанавливать старые узлы `instructions/`, `tools/checkers/`, `LabRenderer`» — то есть проблема наблюдалась вручную и годами не закрывалась инструментом.
- Решение: `arch_critic` получил две проверки. `check_graph` разбирает узлы `Name[Метка<br/>путь]` и сверяет каждый путь с диском; `check_routes` сверяет корни маршрутов из раздела «Ключевые маршруты» с реестром `js/module-registry.js` (у `#workbench/run/<id>` проверяется корень `workbench`, потому что подмаршруты в реестре не объявляются). Обе находки попадают в корзину `adr`, а не `auto`: исчезновение узла — это закрытый или переехавший слой, и ответ («вернуть в схему» или «вывести оттуда») неоднозначен. Проверки схемы ничего не пишут в документы.
- Альтернативы: (1) проверять только паспорт как «главный» документ — отвергнуто: схема отвечает на вопрос «где границы», и именно её читают при разборе инцидента; оставлять её без надзора — тот же дрейф, только в другом файле; (2) генерировать `GRAPH.md` целиком из кода — отвергнуто: схема несёт пояснения («Результаты читаются из API, затем из локального `pipeline-results.json`»), которые из кода не выводятся, а потеря объяснения хуже устаревшей ссылки; (3) проверять все `.md` раздела `01-ARCHITECTURE` — отложено: критерии «факт в тексте» определены для паспорта и схемы, для произвольного документа они потребуют отдельного разбора; (4) считать мёртвый узел обычной опечаткой и править автоматически — отвергнуто: автоматическая правка схемы удалила бы историю решения (почему узел был в схеме и куда он делся), а ADR фиксирует именно её.
- Последствия: разбор вынесен в чистые функции `parse_graph_nodes` / `parse_graph_routes`, чтобы проверки тестировались на синтетической схеме, а чтение файла осталось в `check_graph` / `check_routes`. Регекс маршрутов допускает плейсхолдеры вида `<id>` — без этого подмаршруты молча выпадали из проверки, и тест на это упал. Узлы схемы без конкретного файла (`Docs[docs/00-START + docs/06-METHODOLOGY]`) проверкой не охватываются осознанно: тест требует не меньше шести разобранных узлов, чтобы молчание разбора не выдавало себя за чистоту. Первый прогон на реальном репозитории дал ноль находок — `GRAPH.md` оказался честнее паспорта; это подтверждает, что проверка не ловит шум, но и означает, что её ценность проявится при следующем переезде слоя.

### ADR-010: Дрейф ручного текста паспорта проверяется шаблонами, а не моделью
- Дата: 2026-10-02
- Статус: accepted
- Контекст: ADR-009 закрыл дрейф автоблоков, но ручной текст паспорта остался слепым: в нём «127 корней» против 329 на диске и «44 CSS-файла» против 87 остались бы незамеченными — сканер туда не смотрит. Очевидное решение — позвать LLM и попросить сравнить документ с репозиторием, — воспроизводит ровно ту проблему, от которой ADR-009 уходил: модель выдаёт правдоподобные расхождения без проверки, и в нормативном документе это неотличимо от настоящей находки. Проверяемость здесь важнее полноты.
- Решение: в цикл добавлены два агента. `arch_critic` сверяет ручной текст с фактами по двум шаблонам — «число + существительное» (`87 CSS-файлов` → метрика `css`) и внутрирепозиторные пути; содержимое автоблоков из проверки исключено, шаблоны-глобы (`docs/06-METHODOLOGY/*.md`) и относительные пути лаборатории отфильтрованы. `arch_planner` раскладывает находки в корзины `auto` (правда однозначна), `adr` (затронуто решение) и `manual` (оценочная формулировка, которую автоматика подменила бы мыслью). Ни критик, ни планировщик не имеют доступа на запись: `arch_writer` по-прежнему трогает только маркеры. LLM не вызывается.
- Альтернативы: (1) LLM-сверка ручного текста — отвергнуто: галлюцинации в нормативном документе неотличимы от правды, а цена ошибки (закрепить неверное число в паспорте) выше цены пропуска; (2) перенести все числа в автоблоки и убрать из текста — отвергнуто: числа органично живут в объяснении («21 словарь, 1913 терминов»), вырывание их в таблицу делает паспорт нечитаемым; (3) критик правит ручной текст сам — отвергнуто: это отменяет границу «человек описывает решения, машина описывает факты» из ADR-009; (4) проверять только через `check-docs.py` — отвергнуто: гейт ловит битые ссылки и устаревшие индексы, но не сверяет утверждения с диском, то есть ровно тот класс ошибок, который и копился годами; (5) путь считать только от корня репозитория — отвергнуто: паспорт описывает лабораторию относительной базой (`js/router.js`) и команды из каталога сайта (`bash tools/build.sh` из `products/website`), строгое правило дало бы восемь ложных находок на одной странице.
- Последствия: список показателей критика живёт в `CLAIM_PATTERNS`, список корневых папок для путей — в `PATH_BASES`, а метрики лаборатории считает `arch_scanner.scan_lab_metrics`; расширение любого из этих мест обязано идти вместе с тестом на ложные срабатывания. Планировщик ничего не применяет — предложения живут в пакете до следующего прогона, поэтому человек должен сам прочитать `critique_notes`. Первый прогон после введения критика нашёл ошибку в моей же правке: 67 CSS-файлов вместо 87 (считалось без вложенных каталогов) — то есть проверка окупилась сразу. Следующая фаза, если понадобится, — LLM как второй источник находок поверх шаблонов, с обязательным требованием подтверждения числом; право записи из ручного текста ей не передаётся.

### ADR-009: Паспорт архитектуры разделён на ручной текст и генерируемые фактические блоки
- Дата: 2026-10-02
- Статус: accepted
- Контекст: `docs/01-ARCHITECTURE/ARCHITECTURE.md` разошёлся с репозиторием незаметно: раздел 9 описывал `tools/alephy.py`, `checkers/`, `generators/`, `analyzers/`, `sync/`, `lib/`, `utils/`, которых в проекте нет (каталог `tools/` плоский, 14 скриптов), а в разделе 4 стояли числа трёхлетней давности (127 корней против 329 на диске, 44 CSS против 67). Проверить паспорт было нечем: гейт `check-docs.py` ловит битые ссылки и устаревшие индексы, но не сверяет утверждения документа с диском. Наивное решение — поручить LLM переписывать документ целиком — хуже проблемы: модель переписывает собственный домен и не может проверить саму себя, а паспорт архитектуры после этого перестаёт быть опорой.
- Решение: документ разделён маркерами `<!-- alephy:auto:* -->` на ручную часть (решения, границы, правила) и три генерируемых блока (карта репозитория, точки входа, агентный слой). За блоками стоит пайплайн `arch_keeper`: `arch_scanner` снимает с диска факты без LLM, `arch_writer` считает дрейф и перерисовывает только содержимое маркеров, `arch_convergence` останавливает цикл по подписи «снимок + целевой текст». Запись по умолчанию выключена (dry-run), включается флагом `write_enabled` из кода и только после `generate-docs-index.py` (STATS.md считает строки паспорта, поэтому индексы пересобираются до гейта) и зелёного `check-docs.py`; при красном гейте запись откатывается.
- Альтернативы: (1) LLM переписывает паспорт по запросу — отвергнуто: галлюцинации в нормативном документе неотличимы от правды, а регрессию не ловит ни один гейт; (2) генерировать весь документ из кода — отвергнуто: методологическая часть (принципы, границы, методология ALEPHY) не выводится из кода и была бы потеряна; (3) проверять паспорт в CI новым скриптом в `tools/` — отложено: по сути тот же сканер, но без агентной оболочки; вернёмся, когда накопится история правок; (4) хранить числа в отдельном сгенерированном файле — отвергнуто: паспорт перестал бы быть цельным документом, а читателю пришлось бы держать два открытых файла; (5) сканеру не делать реестровый разбор, только счётчики — отвергнуто: первая же версия объявила дрейфом `pipelines/core.py` (движок) и `scripture_analysis.py` (эндпоинт `POST /api/scripture/analyze` мимо оркестратора, ADR-006).
- Последствия: любая новая точка входа, пайплайн или агент регистрируются в `ENTRYPOINTS` / карточке `pipelines.json` — иначе паспорт расойдётся снова, но теперь это видно на следующем прогоне. `tools/check-docs.py` остаётся обязательным последним шагом: он ловит регрессию в самой генерации. Класс модуля в `pipelines/` влияет на сканер (`ENGINE_MODULES`), поэтому новый движок нужно внести туда же. Фаза 2 (ADR-010) добавила в цикл `arch_critic` и `arch_planner`: ручной текст паспорта проверяется по шаблонам «число + существительное» и по внутрирепозиторным путям, находки раскладываются в корзины `auto` / `adr` / `manual`, но **никто из них не пишет в документ** — правка ручного текста остаётся за человеком.

### ADR-008: Корпус документов лаборатории — указатель коллекции плюс тела по файлам
- Дата: 2026-10-02
- Статус: accepted
- Контекст: 41 маршрут документа читался из трёх JSON-файлов коллекций. Когда в реестр добавились все 21 неучтённых методички `docs/06-METHODOLOGY`, общий файл `data/methodology/documents.json` вырос до 706 КБ (156 КБ gzip) — втрое выше бюджета «страница < 50 KB gzipped». Хубе `#methodology` нужны только заголовки и описания для карточек, то есть пользователь платил за все тела сразу. Параллельно список документов жил в двух местах: карта `GROUP_INDEX_HUBS` в контроллере и флажок достижимости, которого не было, — забытый маршрут оставался живым, но недостижимым.
- Решение: коллекция может объявлять каталог тел (`COLLECTIONS.methodology.dir`), тогда `file` — указатель с `title`/`description`/`source`, а тело лежит в `<dir>/<key>.json`. `docSource()` отдаёт поле `doc`, и `loadCollectionDocument` грузит тело отдельно от указателя; хабу достаётся 10 КБ (2.8 КБ gzip) вместо 706 КБ. Списки групп объявлены одной картой `GROUP_INDEX_HUBS`, а сам факт достижимости проверяет `registry-check.mjs` (запись в карте + вызов `render`/`mountCollectionIndex`) и smoke (число карточек хаба против реестра). Палитра `lab-search.js` индексирует указатели коллекций, а маршрут документа берёт из реестра — ключ без маршрута в палитру не попадает.
- Альтернативы: (1) оставить один файл и грузить его лениво — отвергнуто: список карточек всё равно потребовал бы тела, а разбор 706 КБ на клиенте дороже, чем один запрос на 10 КБ; (2) сжать корпус, хранить Markdown и рендерить на клиенте — отвергнуто: `marked` уже есть, но разметка страницы и её метаданные тогда собирались бы в рантайме, а гейты перестали бы видеть содержимое; (3) вынести методички в отдельный статический сайт — отвергнуто: маршруты реестра, палитра и хаб перестали бы быть одним источником правды; (4) держать 21 файл без маршрутов и считать «служебными» — отвергнуто: это и есть недостижимые документы, только с честным названием.
- Последствия: `docs/06-METHODOLOGY/README.md` и `TEMPLATE.md` остались без маршрутов намеренно — их список закреплён в `registry-check.mjs`, новый `.md` в разделе не пройдёт гейт, пока не станет маршрутом или не попадёт в список служебных. `tools/generate-methodology-docs.py` пишет указатель и тела в lab и build и удаляет осиротевшие файлы, `--check` остаётся гейтом коммита. Гейт `registry-check` сверяет ещё и наличие тела документа на диске. Про Provenance корпуса разоблачения: `data/exposures/documents.json` не выводится из `docs/` (проверено сравнением фрагментов — совпадений нет), поэтому поле `docs` у маршрутов `exposure-*` не объявляется: провенанс должен быть правдой.

### ADR-007: «Карта агентов» заменена вертикальным «Древом агентов» с топологией в коде
- Дата: 2026-10-01
- Статус: accepted
- Контекст: экран «Карта агентов» (`js/agent-map.js`, `css/agent-map.css`) был свободным холстом: узлы таскались мышью, координаты и пользовательские связи лежали в `localStorage` (`alephy_agent_map_v1`), связи рисовались SVG-кривыми и перерисовывались на `resize`. Схема связей при этом не имела источника истины и расходилась с `products/agents/server.py` и линейным порядком пайплайна, то есть показывала то, чего в системе нет. Плюс холст не влезал в канон bento (§5.2a) и требовал отдельной обработки drag&drop, панели настроек роли и удаления связи двойным щелчком.
- Решение: карта удалена, вместо неё экран `#agent-tree-view` (`js/agent-tree.js`, `css/agent-tree.css`, префикс `at-`) — вертикальное дерево ролей в bento-каноне: ячейка 01 (7 колонок) на всю высоту, рельс из 5 колонок с ink-ячейкой «Как читать» и ячейкой «Уровни». Топология (`TREE`, `FEEDBACK`) объявлена в коде рядом с потребителем; агенты, их статусы и иконки по-прежнему берутся из `PageController.getAgentMapData()`, поэтому реестр остался в одном месте. Ствол и ветки — CSS-псевдоэлементы вложенных списков, без SVG и без перерисовки на `resize`. Дерево только для чтения: узел ведёт на существующую страницу агента `#ai-agents/<id>`, где роль, модель и статус редактируются. Сохраняется лишь раскрытость веток (`alephy_agent_tree_collapsed_v1`).
- Альтернативы: (1) оставить карту и починить её — отвергнуто: проблема не в отрисовке, а в том, что у неё нет источника истины; (2) вынести топологию в `data/agents-topology.json` с `fetch` — отвергнуто на этом шаге: статический экран не должен зависеть от сети, а `fetch` без нужды добавил бы офлайн-риск (§9) и второй источник правды об агентах; при появлении динамической топологии (настоящие пайплайны с сервера) вернуться к JSON-источнику; (3) редактирование связей прямо в дереве — отложено: связь, которую не использует сервер, снова станет расхождением, а форма роли уже есть на странице агента; (4) SVG-дерево с координатами — отвергнуто: тащит `viewBox`, `marker-end` и перерисовку связей на `resize` ради статичной структуры.
- Последствия: удалены `js/agent-map.js`, `css/agent-map.css` и их зеркала в `build/`, кнопка тулбара переименована в `.agent-toolbar-tree` (`data-agent-tree-open`, иконка `network`). Ключ `alephy_agent_map_v1` в `localStorage` намеренно не чистится — это данные пользователя; при появлении миграции состояний его можно удалить одной строкой. `agentsDebug` получил `getIcon`, чтобы дерево не дублировало словарь иконок. Изменение роли агента, его статуса или модели требует правки `getAgentMapData()`; появление нового агента — записи в `getAgentMapData()` и в `TREE`, иначе он не попадёт в дерево. Экран не deep-linkится: `#ai-agents` всегда открывает список.

### ADR-006: ИИ-разбор палео-фрагмента — отдельный эндпоинт со слотами и разделением «факт / трактовка / гипотеза»
- Дата: 2026-09-30
- Статус: accepted
- Контекст: в «Книгочтении» был единственный вызов ИИ — `requestAIAnalysis()` в `js/scripture-reader.js`. Он уходил на `http://localhost:8000/api/run`, тогда как единственный агентный сервер проекта — `products/agents/server.py` (`/run`, `/api/run`, §9 `.clinerules`); ошибка проглатывалась пустым `catch`, состояния загрузки и повтора не было, ответ вставлялся одной строкой `escapeHtml(text)` без структуры, а агентом значился `researcher` вместо палео-переводчика. Отдельно: модель получала палео-фрагмент без локально посчитанной физики букв и потому могла выдумать значения о буквах — то есть подменить методологию проекта.
- Решение: (1) новый эндпоинт `POST /api/scripture/analyze` (`products/agents/server.py`), который не переиспользует `/run`: у задачи другая форма ответа. Логика разбора живёт в `products/agents/pipelines/scripture_analysis.py` и не зависит от Flask. (2) Ответ — структурированные слоты `fact` / `interpretation` / `hypothesis` / `warnings[]` / `confidence ∈ {low, mid, high}`; `normalize_slots()` гарантирует форму независимо от того, что вернула модель, а `parse_slots()` достаёт JSON из ответа с посторонним текстом. (3) **Разделение труда: локальная физика букв — факт модуля, модель её не переписывает.** В промпт уходит `localPhysics` (корень из `roots.json`, сборка-действие, паспорт букв), а в правилах запрещено вводить свои значения о буквах. (4) Сбой модели не отменяет ответ: сервер возвращает локальные факты с `modelAvailable: false` и `modelError`, поэтому клиент показывает офлайн-состояние, а не пустую ячейку (§9). (5) Клиентская часть — `js/scripture-ai.js`: берёт разбор у `ScriptureReader.currentEvidence()`, хост/порт читает из настроек панели «Запуск сервера» (`alephy_agent_server_v2`), кэширует ответ по ключу `книга|глава|стих|режим|палео`. Модуль чтения о сети не знает ничего.
- Альтернативы: (1) переиспользовать `/run` с агентом `paleo_translator` — отвергнуто: `/run` возвращает свободный текст или словарь результата агентов, а бенто-ячейке нужен фиксированный набор полей и разделение уровней уверенности; (2) хардкод адреса сервера в модуле — отвергнуто: это создаёт второй источник правды о сервере и уже дало баг (порт 8000); (3) просить моделью «переписать физику» — отвергнуто: палео-физика задана `PALEO_STANDARD.md` и словарём, переписывание сделало бы модуль недетерминированным и методологически неподконтрольным; (4) встроить разбор на клиенте без сервера — отвергнуто: нет доступа к агентам и `roots.json` агентной стороны, а локальный fallback всё равно нужен отдельно; (5) хранить историю разборов на сервере — отложено: первая версия ограничена кэшем в браузере, серверного хранилища в проекте нет.
- Последствия: новая точка входа API требует записи в `docs/01-ARCHITECTURE/ARCHITECTURE.md` (раздел API) при следующем обновлении архитектурного описания. Ответ модели никогда не должен печататься в слоте «факт» без локальной опоры — при добавлении новых слотов их нужно регистрировать в `SLOTS` и в `normalize_slots()`, иначе поле молча пропадёт из ответа. Кэш в `localStorage` не разделяется между профилями; при 40 записях старые вытесняются. Модель подключается через существующий `ollama_adapter` (`generate()`), поэтому новая зависимость не появилась и бюджет бандла не затронут.

### ADR-005: Гейт перед коммитом и режимы агента заимствованы из ECC
- Дата: 2026-09-29
- Статус: accepted
- Контекст: правила проекта (`.clinerules`) описывали, что проверять, но не давали способа проверить это одной командой: пункт «проверки соответствующего уровня» и пункт self-review жили в голове агента и пропускались при усталости контекста. Репозиторий ECC (affaan-m/ECC) решает ту же задачу иначе — pre-commit хук плюс лёгкие режимные контексты (`contexts/dev|research|review.md` по 400–600 байт). Проверено: у нас уже есть соседние гейты (`check-docs.py`, `check-build-sync.py`), и они страдают от того же — их нужно помнить и вызывать вручную.
- Решение: (1) `tools/check-commit.py` — единый гейт по индексу `git diff --cached`: конвенция сообщения §6 (type/scope из белых списков), секреты (error), build-паритет Research Lab (error, переиспользует `check-build-sync.py` как модуль), гейт документации при затронутом `docs/` (error), отладочный мусор (warn). (2) `.githooks/pre-commit` запускает его; включение добровольное через `git config core.hooksPath .githooks`, обход — `--no-verify`. (3) `docs/03-AI/AGENT-MODES.md` — три режима агента, вытесненные в отдельный документ, чтобы `.clinerules` не разрастался.
- Альтернативы: (1) скопировать хуки ECC целиком — отвергнуто: они завязаны на `~/.claude` и plugin-загрузчик, в проекте Cline и лишний node-контур; (2) `pre-commit` фреймворк с `.pre-commit-config.yaml` — отвергнуто: новая зависимость и отдельный env ради пяти проверок, которые уже есть в `tools/`; (3) только текстовые правила в `.clinerules` без скрипта — отвергнуто: ровно то, что было до этого решения, и оно не срабатывало; (4) встроить гейты в `check-docs.py` — отвергнуто: разные фазы (индекс git против корпуса docs), смешивание ломало бы независимые вызовы.
- Последствия: гейт не блокирует коммит сам по себе, пока не включён hooksPath — это осознанно, принудительный хук ломает чужие рабочие сценарии (`git commit` из GUI, аварийные фиксы). Список type/scope продублирован в `.clinerules` §6 и в `tools/check-commit.py`: расхождение лечится правкой обоих; при изменении конвенции это обязательный шаг. Проверки docs/build запускаются только когда затронуты соответствующие пути, поэтому на коммит без `docs/` гейт остаётся быстрым.

### ADR-004: Модуль «Дизайн-система» (`#design-system`) читает токены в рантайме
- Дата: 2026-09-27
- Статус: accepted
- Контекст: канон дизайн-системы жил только в `docs/10-DESIGN/DESIGN-SYSTEM.md` — вне продукта. Расхождение «документ ↔ код» не ловилось ничем: токен можно было переименовать, и витрина продолжала бы показывать старое имя. Дублировать значения токенов в разметке модуля нельзя — это гарантированный дрейф.
- Решение: модуль `#design-system` (реестр → `router.js` → `page-controller.js` → `js/design-system.js` + `css/design-system.css`, префикс `ds-`, bento по DESIGN-SYSTEM §5.2c) читает значения через `getComputedStyle(document.documentElement)` в момент рендера. Носители значения помечены `data-ds-token`, а `MutationObserver` на атрибуте `data-theme` пересчитывает подписи на месте — `page-controller` пропускает повторный рендер уже загруженной панели (`dataset.loaded`), поэтому без наблюдателя витрина показывала бы цвета предыдущей темы. Измеренный долг по контрасту печатается в модуле явно (`.lab-btn-primary` 2.73:1, `.lab-btn-secondary` 2.94:1 при требовании §7 ≥4.5:1), а не правится молча: правка затрагивает все модули лаборатории.
- Альтернативы: (1) статическая таблица значений в разметке — отвергнута: немедленный дрейф при первом же переименовании токена; (2) генерировать страницу из `css/tokens.css` на этапе сборки — отвергнута: нужен новый build-шаг и парсер CSS ради витрины, а «слепок» всё равно устаревает между сборками; (3) чинить контраст кнопок в этом же модуле — отвергнуто: `.lab-btn-*` общий для 97 маршрутов, визуальная регрессия будет системной и не помещается в объём задачи.
- Последствия: добавление роли в §1.1 = одна запись в `COLOR_ROLES` (`js/design-system.js`) + строка в локалях; smoke-тест сверяет подпись образца с токеном и `fontSize` лестницы с `--text-3xl`, поэтому подмена значения или класса роняет прогон. Отдельная задача: поднять контраст `.lab-btn-primary`/`.lab-btn-secondary` до AA — требует ADR, поскольку меняет все кнопки лаборатории.

### ADR-003: Модель локализации сайта (ru — язык разметки, status ready/draft, локали рядом со скриптом)
- Дата: 2026-09-17
- Статус: accepted
- Контекст: сайту нужны RU/EN/HE без сборщика и зависимостей; текст не должен мигать при загрузке, а хеш занят роутером Research Lab (`#route`) — хранить язык в хеше нельзя. Переводы неполные: неготовый язык не должен попадать к пользователю. Проверять паритет ключей и «ключ есть в разметке, но нет в словаре» вручную ненадёжно, поэтому нужен машинный гейт.
- Решение:
  1. Русский — язык разметки: `ru.json` в браузер не грузится (ноль лишних запросов, ноль мигания), текст берётся из HTML/JS; поэтому у элементов с `data-i18n` русский текст обязан оставаться на месте.
  2. Язык определяется по `?lang=` → `localStorage.alephy-lang` → `ru`; хеш не используется, переключение идёт через `location.replace` и не ломает deep-link лабы.
  3. `products/website/src/locales/index.json` — манифест: `default`, `languages[].status` (`ready` — попадает к пользователю, `draft` — виден в переключателе, но отключён), `dir` (RTL), `coverage`.
  4. Локали лежат рядом со скриптом (`build/js/i18n.js` → `build/locales/`), путь берётся из абсолютного `src` — работает при суб-пути хостинга `/alephy/` и на любой глубине страницы.
  5. Единицы перевода: `data-i18n`, `data-i18n-attr="атрибут:ключ"`, `t('ключ', 'русский резерв')`, карта `BURGER_KEYS`; при 404 локалей рантайм тихо деградирует до русского без `console.error` (smoke-прогон падает на ошибках консоли).
  6. Покрытие = (переведённые ключи интерфейса + непокрытые русские строки, если это язык разметки) / (ключи + непокрытые строки); метрика приблизительная: единица — элемент разметки с русским текстом.
  7. Гейты: `tools/i18n-check.py` (ошибки: словарь и манифест, паритет, ключи разметки и JS, пустые ключи активного языка; warn: непокрытые строки, неиспользуемые ключи, расхождение покрытия, русский текст разметки ≠ словарю), `tools/i18n-extract.py check|write|report`, `tools/i18n-verify.mjs` (50 функциональных проверок рантайма), CI `.github/workflows/i18n-check.yml`.
- Альтернативы: i18n-библиотека (i18next и др.) — отвергнута: лишняя зависимость против бюджета бандла и договора ES5-файла на сайт и лабу; язык в хеше — отвергнут: ломает маршруты лабы; словарь ru в браузере — отвергнут: лишний запрос и мигание первого рендера; машинная запись переводов (вместо правки человеком) — отвергнута: машина не знает смысла строки, поэтому `write` только добавляет отсутствующие ключи.
- Последствия: новый язык = `src/locales/<код>.json` + запись в манифест со `status: draft`; включение языка = `status: ready`, после чего гейт требует заполненных ключей интерфейса. Непокрытые русские строки (фаза 1: 140 в страницах сайта) станут `phrases.*` в фазе 3. Research Lab подключается к тому же рантайму отдельной фазой (тогда `apps/researchlab/sw.js` инвалидируется через `CACHE_NAME`). Известное расхождение на момент решения: русский текст 4 ключей лендинга (`pages.index.title`, `hero_title`, `hero_subtitle`, `section3_title`) разошёлся со словарём — гейт сообщает warn, строки приводятся в порядок в контентной фазе, тогда же пересматривается их перевод EN/HE.

### ADR-002: Схема хронологии палео-таймлайна (era / sortKey / kind / confidence)
- Дата: 2026-09-16
- Статус: accepted
- Контекст: `data/timeline.json` был списком лент со свободной строкой `date`; эра фильтровалась хардкодом ID (дублированные массивы в `countByEra`/`applyFilter`), события не сортировались, deep-link `#timeline/<id>/event/<idx>` генерировался, но не обрабатывался, status-dot выводился эвристикой `getEventStatus` (семантически ложен для истории).
- Решение: единая схема — лента `{id, title, paleoIcon, era, description, events}`, событие `{date, sortKey, kind, confidence, source, links[], description, title}`. `sortKey` — число (до н.э. — отрицательное); чипы-эры строятся из `era` данных (словарь `ERAS`); сортировка включается, только если `sortKey` есть у всех событий ленты; дот = `kind` (event/text/artifact/distortion/concept/glyph/person), бейдж уверенности — по палитре DESIGN-SYSTEM §6; `source` — провенанс к `content/**` или `data/**`; `links[]` — внутренние hash-ссылки на связанные события (`#timeline/<id>/event/<idx>`). Механика сравнения: `#timeline/compare/<idA>/<idB>` — сводная хронология двух датированных лент по `sortKey` (теги A/B, клик ведёт в исходную ленту). Добавлены ленты: `tanakh-chronology` (31 событие), `bashah-chronology` (8), `text-witnesses` (13); существующие 7 лент переведены на схему.
- Альтернативы: библиотека таймлайнов (vis-timeline и т.п.) — отвергнута: зависимость противоречит бюджету бандла (<200KB gz); отдельные JSON на каждую ленту — отвергнуто: дублирует каталог и поиск (⌘K).
- Последствия: новая лента = только запись в `data/timeline.json` (+`era` из словаря `ERAS`); для хронологической сортировки нужно заполнить `sortKey` у всех событий ленты; производные файлы в `products/website/build/apps/researchlab` синхронизируются build-контуром (`products/website/tools/build.sh`).

### ADR-001: Ребрендинг GOLEM → ALEPHY
- Дата: 2026-09-11
- Статус: accepted
- Контекст: решение о переименовании бренда проекта во всех слоях (сайт, лаборатория, документы, docker, агенты, видео).
- Решение: регистро-сохраняющая замена golem/GOLEM/Golem → alephy/ALEPHY/Alephy и кириллических брендовых форм («Голем»/«ГОЛЕМ» со склонениями → «Алефи»/«АЛЕФИ») кодмодом `tools/rebrand-alephy.mjs`. Переименованы ассеты (golem-logo/symbol → alephy-*), `docs/14-APPS/GOLEM.md` → `ALEPHY.md`, docker-сервис/сеть/volume, ключи localStorage (`golem_theme` → `alephy_theme` и др.), идентификаторы `GolemState/GolemUI/GolemParser/GolemAPI`.

- Последствия и защищённые зоны:
